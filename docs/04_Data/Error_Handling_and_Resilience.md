# Error Handling and Resilience

## Purpose

This document is the single table SentinelAI's error-handling code should be checked against: for every failure mode named across the project so far, what detects it, what the system does, and — critically — whether it can ever affect a PASS/BLOCK verdict. Nothing here introduces new behavior that contradicts `Aggregates_and_Boundaries.md`'s T1/T2/T3 definitions; this document collects and completes what was already decided, plus closes the small number of gaps (SQLite write failure, invalid configuration) that no prior document fully addressed.

## The One Rule Everything Below Follows

**A failure can only ever do one of two things: get absorbed by degradation (the Analysis still reaches a verdict, marked accordingly) or push the Analysis to the terminal `failed` state (no verdict is ever produced).** There is no third outcome — no silent drop, no indefinite hang, no fabricated result. Every row below is one or the other.

## Failure Catalog

| Failure | Detected at | System behavior | Verdict impact |
|---|---|---|---|
| **Invalid webhook** (bad/missing signature) | Webhook receiver, before any parsing | `401`, request discarded immediately — never reaches `correlationId` derivation (`GitHub_Integration.md`) | No Analysis created at all |
| **Duplicate webhook** (redelivery) | `correlationId` idempotency check (Mode A) | Existing `analysisId` returned; no new Analysis, no duplicate scan or status post (`Domain_Events.md`, `Persistence_Strategy.md`) | None — identical to the original |
| **GitHub PR/changed-files retrieval failure** | Pre-T1, after signature+idempotency pass | Retried with backoff (`GitHub_Integration.md`); if exhausted, T1-Failed path fires — Analysis created directly in terminal `failed` status, `failure_reason = 'pr_context_retrieval_failed'` (`Persistence_Strategy.md`) | **No verdict ever produced** for this Analysis — T3 never fires |
| **GitHub status/comment post failure** (after T3) | Notification Dispatch Service | Retried with backoff; if exhausted, `notification.status = 'failed'`, visible via Audit (`Ubiquitous_Language.md`'s Notification/Result distinction) | None — the verdict was already decided and persisted before this point |
| **GitHub rate limit exceeded** | Response headers/`403` body on any outbound call | Treated as transient, subject to the same backoff as a `5xx`, delayed until `X-RateLimit-Reset` (`GitHub_Integration.md`) | None directly — may contribute to retrieval retries being exhausted (see above) |
| **Scanner timeout** | Adapter-enforced `timeout_seconds` (`Data_Model.md`) | T2 writes `status = 'timed_out'`; Orchestrator proceeds with remaining scanners (P-09, QA-03) | None if at least the required minimum of scanners still succeeded — degradation flag `degradation_any_scanner_failed = true` set at T3 |
| **Scanner failure** (non-zero exit) | Adapter reads the subprocess exit code | T2 writes `status = 'failed'`, `exit_code` and `failure_note` recorded; never interpreted as "no findings" | Same as timeout — degraded, not blocked |
| **Scanner crash** (process killed/segfault) | Adapter's own exception handling around subprocess monitoring | The adapter must catch this at its own boundary and resolve to `status = 'failed'`, exactly like a non-zero exit — it must never let an unhandled exception propagate into the Orchestrator (P-09's core promise; subprocess isolation at the OS level already prevents it from crashing the main process, per `C4_Container.md` §4, but the adapter code must not defeat that isolation by re-raising) | Same as timeout — degraded, not blocked |
| **SentinelAI process stopped mid-Analysis** | Startup recovery sweep | Every stale `running` `scanner_execution` → `failed`; every `running` `analysis` re-evaluated against the now-resolved set; T3 proceeds if possible (`Persistence_Strategy.md`'s Crash & Restart Recovery) | Degraded if some scanners are marked `failed` by the sweep, not blocked — unless the Analysis had not yet retrieved PR context at all, in which case it is `failed` (same as any other retrieval failure) |
| **SQLite write failure — verdict-critical (T1 or T3)** | The `INSERT`/`UPDATE` itself raises or fails to commit | Retried with backoff (a handful of attempts, short intervals — this is a local file, not a network call, so failures here are expected to be rare and transient: disk-full, a held OS-level lock). SQLite's own transaction atomicity guarantees a failed commit leaves no partial state — the Analysis remains exactly where it was before the attempt (`running`, or nonexistent, depending on which transaction failed) | **If retries are exhausted, this is treated as an infrastructure incident, not a domain outcome.** The Analysis is never marked `failed` on this basis — that status is reserved for "we determined this PR cannot be analyzed," not "we computed a verdict but couldn't save it." Instead, this is surfaced as a `CRITICAL`-level log event for operator intervention (`Observability_and_Logging.md`) and the Analysis simply remains `running` until the underlying storage issue is resolved and the write can be retried (manually or via the next recovery sweep) |
| **SQLite write failure — secondary (T-Audit, T-Notify, T-Agent, T-Knowledge)** | Same as above, on a non-critical table | Retried on a best-effort basis, logged at `ERROR`; never blocks or retries the primary Analysis flow (`Aggregates_and_Boundaries.md`'s "eventually consistent" components) | None |
| **AI provider unavailable/timeout** | `AIProviderPort` call | Agent Execution → `pending_unavailable`; Report's `aiSection.status = 'pending'`, resumable later (`AI_Agent_Architecture.md` §8, decision 6) | **None, by construction** — the verdict was already fixed at T3, before this call is ever made |
| **Security Knowledge Base unavailable/empty for a query** | Security Investigation Agent's read | Treated identically to "no sufficient knowledge" — `remediation_status = 'insufficient_knowledge'`, never fabricated (`AI_Agent_Architecture.md` §6, decision 5) | None — advisory-only, per P-02 |
| **Security intelligence source unreachable** (Knowledge Refresh Service) | `SecurityIntelligenceSourcePort` call | Logged, refresh cycle for that source skipped this round; Knowledge Base simply doesn't gain new entries until the source is reachable again (`Configuration_and_Secrets.md`) | None — no relationship to any Analysis at all (`Aggregates_and_Boundaries.md`'s Data Management Boundary) |
| **Invalid configuration submitted** (malformed Policy rules, a Repository pointed at a nonexistent Policy, an empty `enabledScanners` list where the request requires at least one) | API request validation, before `T-Repo`/`T-Policy` | Rejected with `400` (`API_Contract.md`'s error model) — never written | No Analysis is affected; nothing was persisted |
| **A Repository with no Policy assigned is somehow reached at Analysis time** (the invariant in `Entities_Value_Objects.md` is expected to prevent this at configuration time, but this row exists so the pipeline itself never fabricates a fallback) | Policy Evaluation Service, immediately before evaluation | The Analysis proceeds to a terminal `failed` state, `failure_reason = 'policy_not_configured'` — see the note below the table on how this relates to `Data_Model.md`'s original scoping of `failed` | **No verdict** — this is exactly the kind of situation the `failed` state exists for: SentinelAI structurally cannot produce a trustworthy verdict, so it produces none |

## Why `failed` Never Grows a Second Meaning

**Note on scope, relative to `Data_Model.md`.** `Data_Model.md` introduced `failed` narrowly, in terms of its one motivating case: PR-context-retrieval failure. This document generalizes that into a scope-independent rule, needed the moment a second, structurally different cause (`policy_not_configured`) also has to resolve to a terminal, no-verdict outcome: **`failed` means SentinelAI determined it cannot produce a trustworthy Security Result for this Analysis; `failure_reason` identifies the concrete cause, and the status itself never encodes which one applied.** This is a deliberate refinement made at this phase of the documentation, not a silent reinterpretation — `Data_Model.md` is not edited here to reflect it, since revising an already-closed document is out of scope for this correction; this document's phrasing is the authoritative statement of the general rule going forward, and any future update to `Data_Model.md` should adopt it explicitly rather than re-derive it.

Two rows above (`pr_context_retrieval_failed`, `policy_not_configured`) both resolve to the same `analysis.status = 'failed'`, distinguished only by `failure_reason`. This is deliberate: `failed` means exactly one thing — *no verdict exists and none ever will for this Analysis* — regardless of which upstream cause produced it. Adding a new `failure_reason` value for a future failure mode (should one appear) is the correct extension; adding a new terminal status is not, since it would fragment a single, simple guarantee ("completed → verdict exists; failed → it doesn't; nothing else is possible") into cases callers have to special-case individually.

## Escalation Path (Operator-Facing, Not Domain-Facing)

The table above deliberately does not prescribe paging/alerting thresholds — that is an operational tuning concern for a single-operator MVP, not an architectural one. What it does fix is the **signal**: every row that says `CRITICAL` or repeated `ERROR` in the table is exactly the set of conditions `Observability_and_Logging.md`'s logging levels are calibrated against, so an operator watching logs (rather than a full alerting stack, which this project's scale doesn't yet justify) has a complete, honest picture of what needs attention versus what is normal, designed-for degradation.
